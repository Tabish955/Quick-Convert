# Phase 4 decision record

This document records the decisions taken during Phase 4 that are not obvious from the code, so the
reasoning is available to anyone who later asks why a dependency or a behaviour looks the way it does.
Decision identifiers continue the table in `ROADMAP.md` section 5.

## D5: document to PDF rendering engine

A DOCX cannot be turned into a PDF by Pandoc alone. Pandoc reads the document, produces HTML or markup,
and hands the final rendering to a separate engine. The choice of engine decides the installer size, the
licence obligations and how close the output looks to the original.

| Option | Size | Licence | Notes |
|---|---|---|---|
| Pandoc to HTML, then wkhtmltopdf | about 86 MB on disk, about 41 MB compressed in the installer | LGPL-3.0 | Browser layout handles tables and images well. wkhtmltopdf has not shipped a release since 0.12.6 in 2020. |
| Pandoc to Typst, `--pdf-engine=typst` | one binary, roughly 15 to 30 MB | MIT | Actively maintained. Typesetting rather than browser layout, so tables and merged cells need checking against real documents. Not evaluated during Phase 4. |
| QuestPDF, in process | negligible | not MIT | Free only below a revenue threshold, ineligible for government and publicly traded organisations, and the whole document model has to be mapped onto its layout API by hand. |
| LaTeX | several hundred MB | free | Rejected on size. |
| LibreOffice in headless mode | about 350 MB | MPL-2.0 | The only option that reproduces Word's page layout. Kept in reserve for D6 below. |
| Word automation | requires Office | commercial | Rejected: depends on software the user may not have. |

**Decision.** Documents are converted with Pandoc producing standalone HTML with embedded resources, and
the HTML is rendered to PDF by wkhtmltopdf. The binary is pinned by version and SHA-256 in
`tools/Get-Wkhtmltopdf.ps1`, invoked as a separate process, and recorded in `THIRD-PARTY-NOTICES.md`.

**Measured evidence.** A 4.76 MB DOCX (4,994,357 bytes) converted in 16.28 s to a 16 page PDF of
73,657 bytes. The tools directory occupies 86.33 MB uncompressed, with an estimated 41 MB added to the
Inno Setup installer.

**Consequences accepted with the decision.** The installer grows by roughly 40 MB. Page size and margins
are fixed by the argument builder rather than taken from the source document. JavaScript is disabled, and
local file access is enabled because the images are inlined into the HTML as data URIs.

**Open question.** The output was described in the acceptance record as reaching close to 73 KB for a
document that carries embedded media, which is smaller than expected if the images reached the PDF. That
needs one check on a machine with the tools installed: open the PDF and confirm the images are present, or
run `pdfimages -list` over it. Until that is confirmed the fidelity half of this decision is unproven.

**Revisit if.** The installer size becomes a complaint; a real user document renders badly; a security
advisory affects the bundled WebKit or Qt; or a Typst comparison on the same sample shows acceptable
tables, in which case the licence becomes MIT and about 40 MB comes off the installer.

## D6: how test fixture binaries are obtained

Several archive tests need real sample files: RAR4, RAR5, header encrypted RAR, encrypted ZIP and
encrypted 7z. Creating RAR requires proprietary tooling, so the files cannot be generated by the build.

**Decision.** The fixtures are not committed. The tests skip themselves when the files are absent, and
`tests/QuickConvert.Engines.Docs.Tests/fixtures/README.md` records how to produce them.

**Consequence.** On a clean checkout the RAR and encrypted archive tests do not run. The suite reports
them as skipped, which is honest, but it also means the RAR behaviour is only exercised on a machine where
someone has placed the fixtures. These files are a few hundred bytes each, so committing them would remove
that gap.

**Revisit.** Before the release that claims RAR support, or as soon as one of those tests would have caught
a regression that manual testing missed.

## D7: per engine concurrency

Video encoding and archive compression do not tolerate the same parallelism as an image resize. Engines
that know their own cost implement `IConcurrencyAwareEngine` and the coordinator respects the hint instead
of applying one global limit. The contract is described in `docs/PHASE_4_SPEC.md` section 2.3.

3. Fixture archives committed, as described under D6.
